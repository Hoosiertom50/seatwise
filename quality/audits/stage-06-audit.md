## 1. Manual-tester / developer / release-decision-maker review

Read the rendered HTML as each persona:

- **Manual tester**: badge label + symbol for every status (never color alone), a real `<table>` for run metadata with `<th scope="row">`, `<details>/<summary>` per test (native keyboard toggling, no custom focus JS needed), and a working free-text search. Objective/expected-outcome/tags/requirements are all shown per test in plain language.
- **Developer investigating a failure**: source link, sanitized stack trace behind a `<details>` disclosure, named Arrange/Act/Assert steps with per-step pass/fail and duration, failure screenshot/trace links, console-message and failed-network-request disclosures. Verified live against a real deliberately-failing test (see Finding 2 below for what this actually turned up).
- **Release decision-maker**: run metadata (commit, environment, base URL, tag expression), summary-card counts, and a "selection: N matched, M excluded by the filter" line meant to answer "did everything that should have run, actually run?" — this is exactly where Finding 1 below was found.

## 2. Cross-checking displayed counts against the JSON and Playwright's own native result

Ran the real suite three ways and compared: (a) the custom reporter's `RunReport` JSON `counts`/`selectionSummary`, (b) Playwright's own terminal summary line (`N passed`/`N failed`/`N flaky`/`N skipped`), (c) manual inspection of which tests actually executed.

- **Full `pnpm pw:test` (198 tests, no filter)**: JSON `counts.initialPass: 198`, sum of all counts = 198, matches Playwright's own "198 passed" exactly. `selectionSummary: { matchedCount: 198, excludedCount: 0 }` — correct here (all 2 real application tests ran).
- **`pnpm pw:run "@readonly" --allow-production` (1 of 2 real application tests)**: JSON `selectionSummary: { matchedCount: 1, excludedCount: 1 }`, filePath/line correctly `e2e/tests/guest-viewing.spec.ts:23` (confirms DEC-019's fix still holds).
- **A raw, non-`pw:run` invocation mixing one application test with several unrelated unit tests** (`playwright test --project=chromium --project=framework-unit e2e/tests/guest-viewing.spec.ts e2e/tests/unit/ids.spec.ts`, 12 tests total, only 1 of the 2 real application tests): this is where **Finding 1** (High, fixed) was caught — see below.
- **A real forced flaky test** (`--retries=1`, fails on attempt 1, passes on attempt 2): native "1 flaky", JSON `status: "retry-pass"`, `attempts: 2`, `counts.retryPass: 1` — agrees exactly, no bug found here.
- **A real `test.skip()` test additionally tagged `@quarantined`**: native "1 skipped", JSON `status: "quarantined"` (not `"skipped"`) — classification itself is correct, but its plain-language explanation was not (**Finding 3**, High, fixed).
- **A real deliberately-failing test with a success checkpoint before the failure**: this is where **Finding 2** (High, fixed) was caught, in the error message and "why failed" text.

## 3. Accessibility, filtering, links, artifact retention, sensitive-data handling

- **Contrast**: computed WCAG relative-luminance contrast ratios for every CSS custom property pair in both declared color schemes. Light mode is fine (5.9:1–7.5:1 for `--pass`/`--fail`/`--warn` against `#fff`). **Dark mode was not** — this is **Finding 4** (High, fixed) below.
- **Keyboard operation**: `<details>/<summary>` gives native Tab/Enter/Space toggling with no custom JS; the search `<input>` and the (non-functional, see Finding 6) status checkbox are both real, Tab-reachable form controls.
- **Filtering**: the free-text search genuinely hides/showing rows (re-verified live in a real browser, both via the existing DOM test and an ad hoc check) — but see Finding 6 (dead status checkbox) and Finding 7 (search matches more than its own label claims) below, both left open as non-blocking.
- **Links**: served the most recent run report via `pnpm pw:report:run <runId>` and `curl`'d the report HTML, its JSON, the linked native Playwright HTML report, and confirmed a `../../../etc/passwd`-style traversal attempt returns 404 (not a leaked file) — all as claimed. Also confirmed programmatically (Node's `path.normalize`/`path.join` behavior on an absolute-looking `safePath`) that the traversal defense holds for several encodings, not just the one case tried. Server was stopped and confirmed no longer running afterward.
- **Sensitive-data handling**: wrote a scratch test with a fake `Bearer sk_live_...` token embedded in a success-checkpoint's validation description and confirmed live that the generated JSON contains `"authorization: [REDACTED]"`, never the raw token — `redact()` is genuinely wired through the reporter end-to-end, not just unit-tested in isolation. **However**, the same sanitize path let raw ANSI terminal escape codes straight through into every error message, stack trace, and step error — **Finding 2** (High, fixed) below, found while reviewing this exact code path.
- **Artifact retention**: failure screenshot/trace paths in the JSON resolve to real files on disk after a run and serve correctly through `pw:report:run`; `nativeReportPath` resolves to a real, existing `html-report/index.html`.

## Corrections made (live, with locking regression tests)

**Finding 1 (HIGH, FIXED) — `excludedCount` silently reported 0 for a run that genuinely excluded a real application test, whenever the invocation also ran non-application tests.** The original formula (`Math.max(0, discoveredApplicationTests.length - matchedIds.size)`) subtracted the count of *every* test that ran (application tests, framework-health, unit tests — anything) from the count of *only* discovered application tests. Reproduced live: `playwright test --project=chromium --project=framework-unit e2e/tests/guest-viewing.spec.ts e2e/tests/unit/ids.spec.ts` ran 1 of the 2 real application tests (`guest-management.spec.ts`'s test never ran) alongside 11 unrelated unit tests — 12 tests ran in total, more than the 2 discovered application tests, so the old formula computed `2 - 12`, clamped to 0, and the report claimed **"0 excluded"** for a run that in fact excluded a real application test. This is exactly the scenario Section 10.2's "tests excluded by the filter" line exists to surface for a release decision-maker, and it was silently wrong.
- **Fix**: `countExcludedApplicationTests` (new, exported, pure function in `normalizedReporter.ts`) now matches by identity (`testId`), not raw count difference: it counts how many of the *specific* discovered application tests are missing from the set of tests that ran, rather than subtracting two differently-scoped totals.
- **Re-verified live after the fix**: the same mixed invocation now reports `selectionSummary: { matchedCount: 12, excludedCount: 1 }` — correct. The full-suite and single-tag-filtered cases (which happened to be correct before, by coincidence of clamping) remain correct after.
- **Locking tests**: new `playwright-framework/tests/normalizedReporter.spec.ts`, `countExcludedApplicationTests` describe block (5 tests) — including the exact reproduction shape (many more non-application tests ran than were discovered) as its own named test, plus zero-discovered and zero-ran edge cases. Confirmed these tests fail against the pre-fix formula (temporarily reverted, re-ran, restored) before trusting them as a lock.

**Finding 2 (HIGH, FIXED) — raw ANSI terminal escape codes were never stripped from error messages, stack traces, step errors, or the "why this failed" summary.** Playwright's own `TestResult.errors[].message`/`.stack` embed SGR color codes (`\x1b[2m`, `\x1b[31m`, ...) for terminal display of the "Expected"/"Received" diff. The reporter's `sanitize()` passed this straight through `redact()` (credential redaction only, no ANSI handling) with no stripping. Reproduced live: a real deliberately-failing test's generated run-report JSON had `errorMessage`/`whyFailed` fields containing literal `[2mexpect([22m[31mreceived[39m...` — confirmed in a real rendered browser page (`page.locator(".error-message").innerText()`) that this garbled text, not clean readable text, is what a manual tester or developer actually sees and would copy-paste. This directly violates Section 10.2's "sanitized stack traces" and the "why this failed" summary's "plain-language" requirement.
- **Fix**: a new `stripAnsi()` (exported, pure) strips `\x1b[...<letter>` CSI sequences before `redact()` runs, inside `sanitize()`. Scoped to the reporter's own `sanitize()`, not the shared `redact()` (e2e/support/redaction.ts) — ANSI stripping is specific to Playwright's own terminal-formatted error text, not a general credential-redaction concern.
- **Re-verified live after the fix**: the same deliberately-failing test's JSON now has a clean `errorMessage`/`whyFailed` with zero `\x1b` characters anywhere in the report, confirmed both in the JSON and via a real rendered page's `innerText()`.
- **Locking tests**: new `stripAnsi` describe block in `normalizedReporter.spec.ts` (3 tests, including a realistic Playwright-shaped `expect()` diff with real embedded ESC bytes, not a hand-wavy approximation). Confirmed failing against the pre-fix `sanitize()` wiring before trusting it.

**Finding 3 (HIGH, FIXED) — a skipped or quarantined test's "why this failed" field falsely claimed the test had failed.** `buildWhyExplanation` had no explicit branch for `"skipped"`/`"quarantined"` — both statuses have zero named steps and are not passing-like/expected-failure/setup-failure/timeout, so both fell through every branch to the final catch-all: `{ whyFailed: "Failed, but no specific failing named step was recorded." }`. Reproduced live with a real `test.skip()`-tagged `@quarantined` test: the generated run-report JSON reported `status: "quarantined"` (correct) alongside `whyFailed: "Failed, but no specific failing named step was recorded."` (false — the test never ran its body at all, so it neither passed nor failed). A release decision-maker or developer reading that field would be actively misled into thinking the test executed and failed.
- **Fix**: an explicit early check in `buildWhyExplanation` returns `{}` (neither `whyPassed` nor `whyFailed`) for `"skipped"`/`"quarantined"` — the honest answer for a test that never ran, rather than fabricating either a pass or a failure narrative. The badge label ("Skipped"/"Quarantined") and the test's own tags already convey the state without a narrative.
- **Re-verified live after the fix**: the same quarantined scratch test's JSON now shows `whyFailed: undefined`, `whyPassed: undefined`.
- **Locking tests**: new `buildWhyExplanation` describe block in `normalizedReporter.spec.ts` (3 tests) — skipped, quarantined, and a control case (an ordinary `consistent-failure` with zero named steps must still get a real `whyFailed`, proving the fix doesn't overreach into real failures). Confirmed the skipped/quarantined tests fail against the pre-fix fallthrough before trusting them.

**Finding 4 (HIGH, FIXED) — the status badge colors (`--pass`/`--fail`/`--warn`) failed WCAG AA contrast in dark mode.** The light-mode values (`#0a6e31`/`#a3231b`/`#8a5a00`) were reused verbatim under `@media (prefers-color-scheme: dark)` — they were chosen for contrast against a *white* background. Computed relative-luminance contrast against the actual dark background (`#14161a`) and card background (`#1f2227`, used by summary cards and the "why" boxes): **2.4–3.1:1**, well under WCAG AA's 4.5:1 minimum for this text size (none of it qualifies for the lower 3:1 "large text" threshold). Verified live in a real Chromium page launched with `colorScheme: "dark"` before touching anything. This directly violates Section 10.1's explicit "sufficient contrast" requirement, and dark mode is not an edge case here — it activates automatically from the OS/browser preference, with no in-report toggle.
- **Fix**: `--pass`/`--fail`/`--warn` are now also redefined inside the dark-mode media query (`#34d399`/`#f87171`/`#fbbf24`), each independently verified to clear 4.5:1 against both the page background and the card background.
- **Re-verified live after the fix**: same real dark-mode Chromium page, badge `color` now `rgb(248, 113, 113)` (`#f87171`) as intended.
- **Locking test**: new test in `runReportHtml.spec.ts` that renders the real representative-status fixture in both `light` and `dark` `page.emulateMedia()` states and computes the actual WCAG contrast ratio (using the same relative-luminance formula, not a hardcoded expectation) for five representative badge classes against both backgrounds, asserting ≥ 4.5:1 in every case. Confirmed this test fails (2.84:1 reported) against the pre-fix CSS before trusting it. (This test needed a file-scoped `/// <reference lib="dom" />` — the shared `tsconfig.json` deliberately has no `"dom"` lib since this is a Node-side project; scoped to this one file only, not a global tsconfig change.)

**Finding 5 (HIGH, FIXED) — `pw:run` printed a confident "Run report: .../<runId>.html" hint even when no run report was ever written.** `pw:run` documents and forwards a `--reporter <value>` flag (its own `--help` text recommends `pnpm pw:run "<expr>" ... --reporter list`). Playwright's CLI treats any `--reporter` flag as replacing its *entire* configured reporter array, not adding to it — so `--reporter list` silently disables both the native `html` reporter and Stage 06's own `normalizedReporter`, and no run-report JSON/HTML is written at all. The CLI's post-run hint printed unconditionally regardless. Reproduced live: `pnpm pw:run "@readonly" --allow-production --reporter list` printed `Run report: artifacts/playwright/runs/run-reports/<runId>.html (pnpm pw:report:run <runId> to open it)` for a runId whose `.html`/`.json` files were confirmed, directly, to not exist on disk. This is a broken-link defect of exactly the kind the audit brief calls out, and it actively misleads: a user trusting the hint gets nothing, with no explanation of why.
- **Fix**: extracted the hint into a new pure, exported, unit-testable module (`playwright-framework/runner/runReportHint.ts`, mirroring the existing `buildPlaywrightInvocation.ts` precedent for testing CLI internals without executing `main()`), `buildRunReportHint(runId, reporterFlag, runReportHtmlExists)`. `run-tests.ts` now checks `existsSync` on the expected path before choosing which message to print — the real hint only when the file genuinely exists, otherwise an honest explanation naming the actual `--reporter` value that caused it when that's the known cause.
- **Re-verified live after the fix**: the same `--reporter list` invocation now prints `No run report was generated for this invocation (--reporter list replaces Playwright's whole configured reporter array, which is how the run report gets written -- omit --reporter to get one).`; the same invocation *without* `--reporter` prints the real hint, and the file was confirmed to exist at that exact path.
- **Locking tests**: new `playwright-framework/tests/runReportHint.spec.ts` (4 tests). Confirmed 3 of the 4 fail against a reverted (pre-fix, unconditional) version before trusting them.

All five fixes were re-verified together: `pnpm exec tsc --noEmit` clean, `pnpm pw:test` 214/214, `pnpm pw:validate` clean (`Total: 214 tests in 22 files`), and every live scenario in "Cross-checking displayed counts" above was re-run after all fixes landed, not just after each individual fix in isolation.

## Findings disclosed and left open (not blocking)

- **Finding 6 (Medium, open)**: the report's "All statuses" `<input type="checkbox">` filter control is entirely non-functional — no event listener is attached to `.status-filter` in the rendered `<script>`, only to the search `<input>`. Confirmed live: unchecking it in a real browser changes nothing (row visibility count identical before/after). It is a real, Tab-reachable, apparently-interactive control that silently does nothing, which could confuse a user who expects it to filter by status — but it does not misrepresent any data (the working search filter remains available, and no test result is hidden or misstated). Left open: the smallest honest fix is either removing the dead checkbox or wiring real per-status checkboxes, and I judged deciding which of those two directions to take as a product decision better made deliberately in a future stage rather than a quick patch during this audit.
- **Finding 7 (Medium, open)**: Section 10.1 asks for "searchable, sortable, and filterable tables where appropriate." The test list has working search (Finding 6 aside) but **no sort control at all** — it is always rendered in a fixed `testId`-ascending order with no way to reorder by status, duration, or attempts. Not blocking (the fixed order is deterministic and the report is still fully usable), but it is a real, disclosed gap against an explicit Section 10.1 requirement, left for a future stage.
- **Finding 8 (Low, open)**: the search box's own help text says "Matches title, test ID, and tags," but the actual implementation matches a row's entire `textContent` (objective, steps, error messages — everything in the collapsed `<details>`), confirmed live with a search term that only appears in a step title. This makes search *more* permissive than documented, not less — no false negative is possible, only an occasional match a user might not expect from the label. Cosmetic/documentation mismatch, not a functional defect.
- **Finding 9 (Low, open)**: `selectionSummary.matchedCount` is defined as "every test that ran in this invocation" (literally `tests.length`), not "application tests matched by the tag filter" — so for a bare `pnpm pw:test` run it reads "198 matched, 0 excluded," which is technically true but answers a slightly different question than the sentence might imply out of context. The report's own "Tag expression: (none -- ran without pw:run's selection)" line sits right next to it and clarifies this, so I judge it non-misleading in context, but it's worth noting for a future stage considering whether `matchedCount` should instead be scoped to application tests specifically (matching `excludedCount`'s scope after this audit's Finding 1 fix) for internal consistency.
- **Coverage note, not a defect**: the acceptance criterion's 6 representative statuses (initial-pass, consistent-failure, timeout, retry-pass, skipped, setup-failure) are all covered by the DOM test suite; `expected-failure` and `quarantined` are not exercised by any automated DOM test (only manually, in this audit, via `renderRunReportHtml` called directly with synthetic fixtures, and via a real `test.skip()`-tagged `@quarantined` test). Both render correctly with no crash. Since the acceptance criterion explicitly names only 6 statuses, this is not a failed criterion, but a future stage adding these two to the DOM suite would close a real gap in automated coverage of all 8 documented categories.

## Verdict

**PASS WITH FINDINGS.** Every Stage 06 acceptance criterion was independently re-verified against the real running app and real Postgres-backed test suite, not trusted from the implementation log: the six representative statuses named in the acceptance criteria render correctly (plus `expected-failure`/`quarantined`, checked manually); every failed test carries actionable evidence; assertion counts are read from Playwright's own recorded steps, never inferred; the report works offline with no absolute paths; and report-generation failure handling was read and matches the documented behavior (JSON preserved, nonzero exit). Five High-severity bugs were found by this audit — none caught by the pre-existing test suite — and fixed live with locking regression tests, each confirmed to fail against its pre-fix code before being trusted: a wrong "tests excluded by the filter" count that could read "0 excluded" when a real application test was skipped; raw ANSI escape codes corrupting error messages and the "why this failed" summary; a skipped/quarantined test's "why this failed" field falsely claiming failure; WCAG-AA-failing status-badge contrast in dark mode; and a "Run report" hint pointing at a file that, for a documented and recommended CLI flag combination, was never written. Two Medium and two Low findings (plus one coverage note) are logged above as open, non-blocking follow-ups for a future stage, consistent with this project's established pattern of disclosing rather than silently fixing everything. Stage 06 may be marked complete on the Progress Dashboard.
