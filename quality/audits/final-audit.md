### Medium

**M1 — Production-safety documentation and error messages overclaim a two-factor gate that the code does not enforce; only the `--allow-production` CLI flag actually matters.**

`PLAYWRIGHT_TESTING.md` (lines 256–259) states a production read-only run "additionally requires **both** `PLAYWRIGHT_ALLOW_PRODUCTION=1` in the environment **and** this specific invocation to pass `--allow-production` explicitly." `run-tests.ts`'s own user-facing refusal message (lines 280–285) and `productionGuard.ts`'s `ProductionMutationBlockedError`/read-only-refusal messages make the same "in addition to the environment variable" claim. This is not what the code does: `run-tests.ts`'s actual preflight (`if (isProduction && !args.allowProduction)`, line 268) never inspects the ambient `env.PLAYWRIGHT_ALLOW_PRODUCTION` at all, and the value it forwards to both the re-check (`assertMutationAllowed`, line 296) and the spawned child (line 328) is `isProduction && args.allowProduction` — synthesized purely from the flag, discarding whatever the ambient env var actually was. Reproduced live: `PRODUCTION_HOSTNAMES=localhost pnpm pw:run "@readonly" --allow-production`, run **without** `PLAYWRIGHT_ALLOW_PRODUCTION=1` set anywhere in the environment, executed the test successfully against the simulated production host.

This is a real, verified documentation/code mismatch, not a hypothetical — but it is **not a weakening of any actual guarantee**: the file's own top-of-module docstring, `parseRunArgs.ts`'s `--help` text, and `schemas.ts`'s `allowProductionFlagPassed` field comment all correctly and consistently describe the real, deliberate design (DEC-017: only a fresh, explicit, per-invocation flag counts; an ambient env var left in a shell is deliberately never trusted). That design satisfies spec Section 9.3's literal requirement ("an explicit production flag in addition to a production URL") on its own. The bug is that three other places (the `PLAYWRIGHT_TESTING.md` prose and two in-CLI error strings) describe a second, independent env-var gate that does not exist, which could give a human auditor or operator false confidence that an extra safety factor is protecting them when it is not. `PRODUCTION_HOSTNAMES` defaults to empty (DEC-005), so this is dormant in the framework's current, undeployed state — no real production system is at risk today.

Not fixed live, consistent with this framework's own established precedent for this class of finding (Stage 10's Findings 1–2 were materially the same shape — a documented mechanism that doesn't work exactly as narrated, with the underlying safety property intact through a different, verified path — and were left disclosed rather than fixed). Recommend a human decide between two directions: (a) implement the second factor for real (require both), which is strictly more conservative and would make the documentation true as written; or (b) correct the three prose locations to describe the actual, already-sound single-factor design. Either is a small, mechanical change; this audit deliberately did not choose one on its own since it changes either a safety-relevant behavior or a safety-relevant claim in a document a human may rely on.
